# Customer Site artifact deployment

Production deployment authority is **Deployment System**. The blocked
`deploy.sh`, `deploy.ps1`, and `deploy.bat` files are retained only to reject
legacy direct-deploy attempts.

## Release flow

```text
local change -> Git commit -> GitHub -> Local Agent isolated build
-> complete artifact -> SHA-256 validation -> Deployment System
-> production activation -> migrations -> optimize -> queue restart -> health
```

Production directories are runtime targets only. They must not contain a Git
workflow, push to GitHub, build artifacts, install Composer/npm dependencies,
or create releases.

## Artifact contract

The Local Agent must build the exact committed SHA in an isolated workspace.
The sealed artifact must contain:

- `artisan`, `bootstrap/app.php`, and `public/index.php`
- `composer.json`, `composer.lock`, `vendor/autoload.php`, and
  `vendor/composer/installed.json`
- `public/build/manifest.json` and built assets
- `.deployment/release-manifest.json`, generated by Deployment System

Before publish, run `php scripts/release-compatibility.php`. The built tree is
validated with `php scripts/validate-release.php <staged-tree>
--commit-sha=<sha>`. A failed gate must leave the active release unchanged.

## Persistent state

The following paths are runtime/customer state and must never come from an
artifact:

- `.env`
- `storage/`, including `installed.lock`, uploads, private attachments,
  sessions, logs, backups, and release/runtime records
- `public/uploads/`
- `public/storage` (the link/reference to `storage/app/public`)

Preferred Deployment System configuration is persistent references for
`storage`, `public/uploads`, and `public/storage`, with `.env` as the only
copy-preserved path. The persistent root must already contain every configured
target before the first activation. Preserve and persistent path lists must not
overlap.

Until persistent references are provisioned, configure the project preserve
list explicitly as `.env`, `storage`, `public/uploads`, and `public/storage`.
The Deployment System default does **not** include `public/uploads`, so relying
on defaults can lose legacy customer media during a release swap.

Never preserve `vendor` or `public/build`; both must come from the new artifact.

## Production steps

After checksum and completeness validation, Deployment System may run only
server-local runtime operations:

1. enter maintenance/drain traffic as configured;
2. atomically activate the staged artifact;
3. run `php artisan migrate --force` after a verified database backup;
4. run `php artisan optimize`;
5. run `php artisan queue:restart` and verify managed workers return;
6. require HTTP 200 from `/api/health` before marking the release healthy.

`storage/` and `bootstrap/cache/` must be writable by the PHP and queue-worker
users. The web server must be able to follow the configured persistent links.

## Rollback

Rollback is a Deployment System operation to a previously validated artifact
and recorded checksum. Do not check out Git commits or run Composer/npm on the
production directory.

Before activation, retain the previous release and take a database backup. A
code rollback is safe only while the database schema remains compatible with
the previous code. If a migration is not backward compatible, restore the
matching database backup as an explicitly authorized recovery step. After
rollback, run optimize, restart queues, and require `/api/health` to return 200.

## First installation

First installation remains separate from release deployment: create persistent
paths, provide `.env`, install the database, run migrations, and complete the
installer so it writes `storage/installed.lock`. That lock is customer runtime
state; it is intentionally absent from Git and release artifacts.
